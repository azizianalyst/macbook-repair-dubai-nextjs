# SEO Architecture Audit

**Site:** MacBook Repair Dubai (Next.js App Router, single Apple-repair workshop, ~330 pages / 8 page types)
**Audit date:** 2026-06-08
**Scope:** Site architecture only — internal linking & silos, hub/spoke equity flow, cannibalization, thin/near-duplicate content, and duplicate/weak `<head>` metadata across all 8 page types. On-page copy quality, backlinks, and Core Web Vitals are out of scope.

## Executive summary

- **The architecture is complete — all 8 page types are present and accounted for:** homepage, device-category hubs (`/iphone-repair-dubai`, `/macbook-air-repair-dubai`, `/imac-repair-dubai`, `/mac-mini|studio|pro-repair-dubai`), device-model pages (29 MacBook + 20 Mac-desktop/iMac + 23 iPad + 23 iPhone + iPod), service/issue pages, location pages (9 emirate/city + 9 Dubai-area + near-me/onsite/where-to), commercial/transactional (sell/trade-in/AMC/AppleCare/insurance/boot-camp), blog/content (82 posts + category hubs + how-to guides), and trust+legal (`/reviews`, `/about`, `/contact`, `/pricing`). No page type is missing. The problems are equity-routing and metadata-generation flaws, not gaps in coverage.
- **Severity counts: 13 high, 21 medium, 17 low.** The dominant theme across the high findings is a single root cause: **rich, hand-authored metadata never reaches the indexed `<head>`.** `useSeo` (`src/hooks/use-seo.ts`) deliberately stopped touching `<title>`/`<meta>` (those are now owned by the App Router Metadata API), but the model templates still pass their `seoTitle`/`seoDescription` only into JSON-LD — so for every data-driven model route the crawler sees slug-templated boilerplate instead.
- **The single most important fix:** populate `src/lib/route-meta.generated.ts` (or add `generateMetadata()` to the model `page.tsx` wrappers) for the **100 indexable routes currently missing explicit meta** — 92 of which share a byte-identical description template. This one workstream resolves five separate high/medium duplicate-meta findings (29 MacBook models, 20 Mac-desktop/iMac models, 23 iPad models, 18 city/area pages, `/imac-screen-repair-dubai`, `/reviews`) and is the highest-leverage change on the site. All source data (per-model AED prices, chips, years) already exists in the JSON content files.
- **Second-biggest theme — broken hub equity flow.** Three high findings show child pages routing their "X Repair" breadcrumb to a *service* page instead of the *hub*: 37 iPhone views point at `/iphone-screen-repair-dubai`, all 7+ iMac model/service views point at `/imac-screen-repair-dubai`. The hubs that are supposed to consolidate authority (`/iphone-repair-dubai`, `/imac-repair-dubai`) receive **zero upward links from their own children**. These are one-line-per-file fixes that simultaneously correct the visible link and the JSON-LD `BreadcrumbList`.
- **Real consolidation needed in two clusters:** `/macbook-thermal-paste-replacement-dubai` is the same service as `/macbook-overheating-fix-dubai` (301-merge), and `/apple-service-center-dubai` is a second full-Apple-range hub competing head-on with `/apple-repair-dubai` (301-merge or re-angle). One blog post (`/blog/macbook-repair-near-me-dubai`) duplicates its service landing page and should 301.
- **Location silo is footer-only.** The mega-menu has zero location links and the area/emirate silos are disjoint rings that never link to each other or up to a hub — a structural high. A new "Locations" mega-menu panel plus cross-links converts two isolated rings into a proper hub-and-spoke graph.

## Findings by category

### Cannibalization

**Overheating Fix = Thermal Paste Replacement (high).** `/macbook-overheating-fix-dubai` and `/macbook-thermal-paste-replacement-dubai` use the identical `SubServicePageTemplate`, target the same user (overheating → repaste + fan clean), have functionally identical `whatWeFix`/`steps` arrays, and differ only AED 20 (300 vs 280). Internal links already favor the overheating URL (Footer, `MacBookModelPage` `buildServiceRows`, `Home.tsx`, blog posts), while thermal-paste is reached only from the Home grid and the "thermal paste" `linkify` trigger. **Fix:** migrate the thermal-paste page's stronger intro paragraphs + 2–3 unique FAQs + the `quickAnswer` schema into the overheating page, add a `/mac-fan-cleaning-dubai` related link, then 301 thermal-paste → overheating-fix; point both `linkify` rules at the overheating URL and remove the slug from `routes.generated.ts` and the `Home.tsx` grid.

**Two full-Apple-range hubs (high).** `/apple-repair-dubai` (title "Apple Repair Dubai - All Devices Since 2004", the mega-menu "Apple Services" top-level) and `/apple-service-center-dubai` (a generic WordPress rebuild with a 23-item SERVICES array duplicating the hub *and* the dedicated `/macbook-*-repair-dubai` pages) are both device-agnostic hubs for the same head term. The service-center page has no distinct angle and is demoted to one link in the "More Apple" column. **Fix:** 301 → `/apple-repair-dubai`; or, to keep the brand-name URL, re-angle it as an AASP-vs-independent explainer and strip the duplicate per-service grid (which currently splits equity with the real service pages).

**Blog "near me" duplicates the landing page (high).** `/blog/macbook-repair-near-me-dubai` (H1 "MacBook Repair Near Me in Dubai - Workshop Location & Service Map") reproduces the same Concord Tower coverage map, free-pickup steps, and parking/metro FAQs as the service landing page `/macbook-repair-near-me` (which carries LocalBusiness + Service schema and a full conversion layout). **Fix:** 301 blog → landing; if a blog is wanted, rewrite to a distinct "how to choose a workshop near you" angle with no H1/title/body overlap.

**Screen page as de-facto iPhone hub (medium).** The two pages target distinct intents (broad-service hub vs screen-only), so this is hub-signal dilution, not classic cannibalization — but all 15 iPhone model breadcrumbs naming "iPhone Repair" point to `/iphone-screen-repair-dubai`, and ~18 first `related[]` entries do too. **Fix:** fold into the 37-file breadcrumb pass; re-point the first `related[]` entry to `/iphone-repair-dubai`.

**Touch ID vs Power Button (medium).** Both pages claim both keywords with conflicting prices (AED 350 vs 250) for the same physical component (the power button doubles as the Touch ID sensor). The Touch Bar page is *not* a co-offender — it owns the OLED-strip faults. **Fix:** power-button page = button mechanics/assembly; Touch ID page = T2/Secure-Enclave pairing + enrolment; remove "power button dead" from the Touch ID title; resolve the price conflict; on the Touch Bar page swap the stray Touch ID bullet for a link.

**iPad screen-price contradiction (medium).** `IPadScreenRepair.tsx` hardcodes iPad 9/10/11 = AED 350, Air 4–7 = 500, Pro 13 M2/M4 = 900, while `ipad-models.json` (rendered on model pages + in `serviceSchema`) has iPad 9th Gen = 580, Air 5 = 940, Pro 13 M4 = 1,560. Two indexed pages emit contradictory Price/Offer signals; the line "iPad 9 with cracked glass... is AED 350" is plainly wrong (actual 580). **Fix:** drive the screen page's `pricingRows` from `ipad-models.json` (one source of truth) or use honest floor prices with a per-model note; correct the wrong copy first.

**Three sell/trade pages (medium).** All share the same skeleton and `TradeInEstimator`; `/sell-macbook-dubai` already absorbs the faulty angle (a "Faulty & spares-or-repair" card + a "Faulty, cracked or dead" article), making `/sell-faulty-macbook-dubai` a near-duplicate. `/trade-in-macbook-dubai` is more differentiated (upgrade-credit framing) but still replicates the four-factor valuation grid. **Fix:** make faulty a child of sell (remove the duplicate faulty section from sell) or 301; trim trade-in to the upgrade path; only `/sell-macbook-dubai` should own the broad "we buy working or faulty" claim.

**Charging-port vs Lightning/USB-C (low).** The broad charging-port page (with a full iPhone 6–17 table labeling rows "(Lightning)"/"(USB-C)") competes with the two narrow pages, but the narrow pages use a lighter template and have genuinely distinct angles (Lightning = free lint-clean-first; USB-C = Thunderbolt/bent-pin). **Fix:** make the broad H1/title symptom-first; add the two narrow pages to the hub's `relatedSlugs` (the hub currently doesn't link down).

**near-me/onsite/area soft overlap (low).** The 9 area pages are well-differentiated (unique towers, drive times, FAQs) and safe. Only `/macbook-repair-near-me` and `/onsite-macbook-repair-dubai` softly overlap (shared static area list); onsite already links to near-me in its FAQ. **Fix:** replace onsite's 8-item AREAS list with one sentence linking to near-me.

**macOS-reinstall slug pair (low).** `/mac-os-reinstall-dubai` (Mac Mini/Studio/Pro) and `/imac-os-reinstall-dubai` are legitimately device-split. The risk is `/macos-reinstall-dubai` vs `/mac-os-reinstall-dubai` differing by one hyphen, both generically named, while the former is MacBook-framed in its breadcrumb/related links but never says "MacBook". **Fix:** add "MacBook" to `/macos-reinstall-dubai` H1/title; cross-link all three.

**Pencil-compatibility vs screen (low).** The pencil page is transactionally configured (`serviceName: "iPad Pencil-Safe Screen Replacement"`, WhatsApp prefill) yet the screen page already sells Pencil preservation. `startingPrice:0` shows it's meant as a sub-service explainer. **Fix:** strip the transactional props, reframe as a compatibility check, keep the body content.

*(unverified)* **Cleaning & Maintenance** shares the "fan and vent clean" angle with the overheating cluster; **two iPhone overheating posts** (15 Pro vs Dubai-summer) overlap but are acceptably distinct — keep, cross-link, monitor.

### Duplicate / weak metadata

**Root cause (applies to all the model findings):** `src/hooks/use-seo.ts` no longer writes `<title>`/`<meta>` (App Router Metadata API owns them) and only injects JSON-LD + LCP preload. The model templates (`MacBookModelPage.tsx` ~256–257, `MacDesktopModelPage.tsx` ~282–283, `IMacModelPage.tsx` ~278–279, `IpadModelPage.tsx` ~230–231) pass rich `seoTitle`/`seoDescription` *only into schema*. Every model `page.tsx` calls `metaForPath()`, which falls back to `deriveMeta()` in `src/lib/page-meta.ts` for any slug missing from `route-meta.generated.ts`.

**The 100-route gap (high).** `routes.generated.ts` has 350 routes; `route-meta.generated.ts` has 247. After excluding `/`, `/admin/leads`, `/landing-template-demo`, exactly 100 indexable routes fall through to `deriveMeta()`. 92 of those match the repair regex and receive the identical description: `"{pretty} by experienced Apple specialists in Dubai. Free diagnosis, same-day service, 90-day warranty. Call 055 741 3706."` — only the slug-derived prefix varies. **Fix:** generate `ROUTE_META` (or per-route `generateMetadata()`) for all 100, priority: 18 city/area → 72 model variants → 7 blog stubs + `/reviews`.

**Per-family model meta (high ×3).** The 29 MacBook, 20 Mac-desktop/iMac, and 23 iPad model routes are each a subset of the 100 above. Their data (chip, year, per-repair AED) already exists in the JSON content files; the generator simply was never extended to emit model entries. **Fix:** extend the generator or add `generateMetadata()` to the model `page.tsx` wrappers (keeps the JSON as single source of truth).

**Keyword-stuffed MacBook titles (high).** `deriveMeta()` builds `${pretty} | ${SITE_NAME}` where both `pretty` (from the `-repair-dubai` slug) and `SITE_NAME` end in "Repair Dubai" — e.g. "MacBook Pro 14 M5 Pro 2026 Repair Dubai | MacBook Repair Dubai". **Fix:** when `pretty` already ends "Repair Dubai" (case-insensitive), strip/replace the brand suffix.

**18 city/area pages (high).** None of the 18 slugs exist in `route-meta.generated.ts`; all get the boilerplate description with only the location swapped. ## Notes & assumptions

- **Methodology.** This is a data-driven, registry-based site: routes live in `src/lib/routes.generated.ts`, indexed metadata in `src/lib/route-meta.generated.ts` (built by `scripts/extract-meta.cjs`), and model/location content in JSON/TS files (`macbook-air-models.json`, `macbook-pro-models.json`, `mac-desktop-models.json`, `imac-models.json`, `ipad-models.json`, `iphone-models.ts`, `cities.ts`, `areas.ts`, `mega-menu.ts`, `blog-index.ts`, `blog-posts.ts`). The audit cross-references these registries (route count vs meta-key count, `BLOG_INDEX` vs `blog-posts.ts`, breadcrumb paths vs hub slugs) rather than crawling rendered HTML, which is why findings cite exact files and line numbers.
- **Adversarial verification.** Every High/Medium finding above the unverified marker was independently re-checked against the actual source files; several were corrected during verification — three cannibalization claims were **downgraded** (the iPhone screen-vs-hub overlap is hub-dilution not search cannibalization; the near-me/onsite/area cluster is a 2-page soft overlap not an 11-page cluster; charging-port overlap is mild given distinct templates), and one orphan/duplicate-meta severity was reduced because the impact is confined to an internal related-links widget, not Google-visible `<head>` tags. Findings still marked **(unverified)** carry `verified:false` in the source data and should be spot-checked before action — they are largely mechanical title/description-length trims and secondary internal-link additions, low-risk but unconfirmed at the file level.
- **The central technical assumption** is that `useSeo` is intentionally schema-only (confirmed by its own in-file comment) and the App Router Metadata API is the sole owner of `<title>`/`<meta>`. If that ever changes, the duplicate-meta findings would need re-evaluation. Until then, fixing `route-meta.generated.ts` (or adding `generateMetadata()`) is the only way to get authored copy into the indexed head.
- **Needs human judgement:** (1) the conflicting prices (Touch ID AED 350 vs Power Button 250; iPad screen-page buckets vs model JSON; iPhone screen/battery floor prices) require a business decision on the *correct* number before any code change — the audit can only flag the contradiction. (2) The 301-merge calls (`thermal-paste`, `apple-service-center`, `sell-faulty`, the near-me blog) assume no material backlink equity worth preserving on the source URLs; check Search Console / a backlink tool first — if links exist, the 301 (not deletion) is mandatory and content migration should precede it. (3) `currentInLineup` flags encode a point-in-time fact (Apple's June 2026 lineup) and will need periodic maintenance regardless of this fix.
